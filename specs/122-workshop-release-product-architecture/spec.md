# Spec 122 — Workshop, Release, and Product Architecture

**Created:** 2026-07-17  
**Status:** Approved specification; implementation pending staged approval  
**Domain:** ZPK system + private Studio/Admin + public storefront + Firebase backend  
**Deployment:** Firebase, private Pages (`origin/main`), and public storefront (`public/main`)

## Authority

This specification consolidates the permanent FlowVault product-structure rules and the complete architecture discussion that preceded Spec 122. If legacy storefront behavior conflicts with this document, this document governs the migration target while the compatibility requirements below govern the transition.

## Permanent product hierarchy

```text
Design DNA (internal)
└── Collection (public family)
    └── Design Model (genuinely distinct design)
        ├── Color / Material Variant
        ├── Widget Edition
        ├── Technical Variant (device/resolution target)
        └── Revision (technical fix/improvement)
```

Rules:

1. A different color or material is a Variant, never another numbered Design Model.
2. A fixed widget selection is an Edition when the background and main composition remain the same.
3. A materially redesigned dial is another Design Model.
4. A resolution/device adaptation is a Technical Variant, never another artistic product.
5. A bug fix or technical improvement is a Revision.
6. Physical Amazfit/Zepp watch models are called **Devices** in application-domain code and UI. `Model` is reserved for FlowVault Design Models.
7. A sellable SKU is the combination of Design Model + Color/Material Variant + Widget Edition.
8. A Technical Package is a device-specific ZPK attached to a SKU; it is not independently sellable.
9. Customers receive every compatible current Technical Package included by their purchased SKU entitlement.
10. FlowVault watchfaces are finished, non-editable digital timepieces, not customer templates.

## Problem

The current system flattens each uploaded ZPK into a catalog product. The generated testing name is embedded into the ZPK before separate store metadata is entered. Studio upload and Admin enablement act as inconsistent publication paths. `OFFLINE` is presented as soft deletion, while a separate hard-delete endpoint can silently leave Storage objects. The cloud does not retain the exact `.fvwf` editor project paired with each physical-watch test. The public storefront, checkout, orders, and downloads all identify one ZPK as the purchased product, which cannot represent variants, editions, bundles, device packages, or revisions correctly.

## Goals

1. Separate unrestricted design/testing work from curated store publication.
2. Save the exact editable `.fvwf` and installable test `.zpk` for every intentional physical-watch test build.
3. Organize trials under Workshop Projects without requiring commercial classification.
4. Provide one authoritative guided promotion/release workflow from both Studio and Admin.
5. Derive canonical names and product codes from controlled hierarchy selections.
6. Create a released ZPK by metadata-only repacking of the approved, physically tested ZPK.
7. Prove that no functional payload changed during release repacking.
8. Model public Design Models, SKUs, Technical Packages, Offers, entitlements, and compatible Devices explicitly.
9. Distinguish Live, Offline, Archive, Trash, Restore, and Permanent Delete operations.
10. Preserve existing public links, catalog data, orders, and downloads during migration.

## Non-goals

1. Customers may not edit or rebuild purchased FlowVault designs.
2. Ordinary editor autosaves are not uploaded as Workshop Builds.
3. A ZPK is not parsed back into an editable canvas; the paired `.fvwf` is authoritative.
4. Commercial hierarchy fields are not mandatory while experimenting.
5. Store categories, Design DNA, prices, offers, and merchandising tags are not injected into the ZPK unless required by the Zepp package contract.
6. Existing working generator, rendering, layout, or asset-baking logic is not rewritten for this feature.

## Functional requirements

### FR-1 Workshop Projects

1. A Workshop Project groups related experiments and builds.
2. Required project input is only a working title, autogenerated when empty.
3. Optional organization includes folder/group, notes, tags, and target Device.
4. Design DNA, Collection, Design Model, Variant, and Edition remain optional until promotion.
5. A project exposes its current build, build count, storage usage, and released-product linkage.

### FR-2 Workshop Builds

1. `Create Watch Test` replaces the misleading test-time meaning of `Publish ZPK`.
2. One intentional test action creates one numbered immutable Workshop Build snapshot.
3. The build stores the exact pre-export `.fvwf`, exact generated test ZPK, MAIN preview, AOD preview, creation time, target metadata, notes, and parent build.
4. The `.fvwf` must include the complete editor-restoration payload currently used by local project loading, including embedded background state and editor-local MAIN/AOD state.
5. Test-time names are free-form `workshopLabel` values and may be autogenerated with date/build number.
6. No store metadata or price is required to create a test build.
7. Builds support Download FVWF, Download Test ZPK, Open in Studio, Mark Approved, Move to Trash, and history navigation.
8. A completed Watch Test creates the same Zepp `zpkd1://` QR artifact as the established ZPK flow, but stores the QR and its exact Test ZPK under the immutable Workshop Build path; generating it does not publish or classify the build.
9. If Workshop persistence fails after local generation, Studio retains the exact FVWF/ZPK artifacts in memory and offers retry without rebuilding them.

### FR-3 Open in Studio

1. Admin opens `/studio?workshopProject=<id>&build=<id>` in a new tab.
2. Studio authenticates the Admin, fetches the authorized `.fvwf`, and asks before replacing the current canvas.
3. Loading uses the existing `.fvwf` import/normalization path.
4. Saving another physical test creates the next numbered build in the same Workshop Project.
5. The ZPK is never treated as the editable source.

### FR-4 Guided promotion and release

1. Studio and Admin launch the same release-wizard component and backend command.
2. An unprepared build cannot be enabled directly.
3. The wizard selects or creates, in order: Design DNA, Collection, Design Model, Color/Material Variant, Widget Edition, Technical Variant, Revision, and Offer.
4. Each create/select step performs normalized duplicate detection.
5. Technical Variant is detected from Device/spec-group metadata and confirmed rather than freely invented.
6. Revision defaults to `v1.0` for the first package and the next valid revision for an existing SKU/target.
7. The wizard explains the permanent classification decision at each artistic hierarchy step.
8. The review step displays the hierarchy, canonical customer name, internal code, technical target, regular price, campaign price, and every conflict/duplicate result.
9. Final actions are `Save as Ready` and `Release to Store`.

### FR-5 Canonical naming

1. A Workshop label is never authoritative for a released package.
2. The customer name is generated, not freely typed:

   `FlowVault <Design Model> — <Variant> — <Edition>`

3. Optional components are omitted cleanly when the product has no distinct Edition/Variant.
4. The internal code follows:

   `FVL-<collection>-<model>-<variant>-<edition>-<technical-target>-<revision>`

5. Duplicate checks are case-insensitive and punctuation/spacing normalized.
6. Release activation fails when the embedded ZPK name differs from the generated canonical name.

### FR-6 Metadata-only release repack

1. The approved test ZPK is the immutable functional source of the released package.
2. Release creates a derivative copy; it never mutates the approved test object.
3. The repacker may change only allowlisted embedded `appName`, name-bearing description, and outer display/filename metadata fields.
4. The repacker must handle every applicable outer, app-side, and device-side manifest location.
5. It must not rerun generators, renderers, asset baking, layout calculation, or package synthesis.
6. SHA-256 verification must prove JS, images, layout/configuration, target metadata, and all other non-allowlisted payloads are unchanged.
7. Release fails closed if an unexpected entry or field differs.
8. The parity report is stored with the Technical Package release record.

### FR-7 Store hierarchy and merchandising

1. Design DNA is an internal creative classification.
2. Collection is a public design family.
3. Design Model is the primary public catalog and SEO object.
4. Variant + Edition defines a sellable SKU.
5. Technical Packages attach to SKU + Technical Variant + Revision.
6. Offers express an individual SKU or bundle of SKUs and own pricing/campaign logic.
7. Complete Color Collections use premium permanent wording, not “version pack.”
8. Regular and soft-opening prices follow the permanent strategy unless explicitly updated in authoritative business configuration:
   - Individual: $8 regular / $4 soft-opening.
   - Three-color Complete Color Collection: $16 regular / $12 soft-opening.
9. Catalog reporting distinguishes Unique Design Models from Sellable SKUs.

### FR-8 Public storefront

1. One public page and catalog card represents one Design Model.
2. Variants and Editions are selectors within that page, not duplicate model cards.
3. Technical compatibility is not presented as another artistic product.
4. Collection pages show public family narrative and their Design Models.
5. Device pages list compatible Design Models and use `/devices/:deviceSlug` terminology.
6. Cards show Collection, variant/edition counts, price-from, swatches, bundle availability, and compatibility summary where available.
7. Product pages include MAIN/AOD media, Variant/Edition selection, individual/bundle offer selection, Device compatibility, and finished-timepiece messaging.
8. Legacy `/face/:id`, `/model/:slug`, `/buy/:id`, and order/download links resolve through compatibility adapters or redirects.

### FR-9 Checkout, entitlement, and fulfillment

1. New checkout is server-authoritative by `offerId`, never a raw ZPK path.
2. Orders store immutable offer, included-SKU, price, currency, and entitlement snapshots.
3. Fulfillment maps selected Device to Technical Variant and resolves the current READY/CURRENT package for every owned SKU.
4. A Complete Color Collection returns every included compatible SKU package.
5. New device support and revisions may expand fulfillment for existing owners without another purchase.
6. Legacy `productId` orders and download tokens remain valid.
7. Purchased/current packages cannot be permanently deleted.

### FR-10 Lifecycle and deletion

1. Workshop Build states: `TESTING`, `APPROVED`, `PROMOTED`, `TRASHED`.
2. Store Product states: `DRAFT`, `READY`, `LIVE`, `OFFLINE`, `ARCHIVED`.
3. Technical Package states: `BUILDING`, `VALIDATING`, `READY`, `CURRENT`, `SUPERSEDED`, `FAILED`, `TRASHED`.
4. `Take Offline` preserves records, assets, entitlements, and purchase history.
5. `Move to Trash` records deletion time, actor, reason, and previous state without deleting data.
6. `Restore` returns a trashed record to its valid previous state.
7. `Delete Permanently` is available only from Trash and requires typed confirmation.
8. Server-side hard deletion must reject current, promoted-required, purchased, or otherwise referenced packages.
9. Every expected Storage deletion result must be checked; unexpected failures prevent Firestore deletion and are reported.
10. An orphan scanner identifies historical/unreferenced Storage objects and never deletes automatically.
11. Admin exposes Workshop, Store Products, Releases, Trash, and maintenance views.

### FR-11 Storage and retention

1. Binary artifacts remain in Cloud Storage; Firestore stores metadata and references.
2. Ordinary editor autosaves remain local; only `Create Watch Test` uploads a snapshot.
3. Admin shows project/build/Trash/orphan storage totals.
4. The system may suggest configurable cleanup of rejected old builds but never auto-deletes without explicit policy and confirmation.
5. Approved, promoted, current, purchased, and audit-required artifacts are retained.
6. Uploads must use an appropriate authenticated binary-upload mechanism rather than expanding large `.fvwf` payloads inside a constrained JSON Function request.

### FR-12 Security and deployment

1. All Workshop, release, lifecycle, and deletion mutations require Firebase ID-token authentication and Admin authorization.
2. The public target exposes only public read/checkout/download surfaces.
3. No browser PAT or direct GitHub mutation fallback is introduced.
4. Firebase Functions are built and deployed with explicit project and targeted endpoint lists.
5. Firestore rules/indexes are deployed explicitly if changed.
6. Public and private builds and live routes pass the canonical SpecKit deployment gates.

## Compatibility and migration requirements

1. No existing records are automatically grouped into variants based only on similar names.
2. Each legacy catalog entry initially maps to one temporary Design Model, one default SKU, and one Technical Package.
3. Admin provides a reviewed classification queue for manual consolidation.
4. Old IDs remain resolvable through a legacy-ID mapping.
5. Existing orders keep their original product entitlement and download behavior.
6. Migration is additive and reversible until explicit cutover.
7. Legacy `ENABLED/OFFLINE` semantics remain readable during transition.
8. Historical Storage layouts are included in orphan discovery and deletion diagnostics.

## Acceptance criteria

1. A user can create 100 test builds without completing a single store field.
2. Each test build can reopen the exact `.fvwf` and download the paired exact ZPK.
3. Studio and Admin invoke one identical release wizard.
4. Direct enabling of incomplete test builds is impossible.
5. A released package displays the canonical name on watch.
6. Repack verification proves that only allowlisted name metadata differs from the approved test ZPK.
7. One Design Model with three colors appears as one catalog card and three selectable SKUs.
8. A device/resolution adaptation creates another Technical Package, not another SKU/card.
9. Offline records remain restorable; trashed records remain restorable; permanent deletion removes verified objects or fails visibly.
10. An orphan scan explains existing Firebase residue without destructive automation.
11. A Complete Color Collection grants and fulfills all included compatible SKUs.
12. Legacy store URLs and paid downloads continue to work.
13. Public builds contain no private routes; private routes remain guarded.
14. Firebase, private Pages, and public Pages deployment verification all pass before closure.
